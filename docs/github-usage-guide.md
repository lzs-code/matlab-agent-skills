## 一、核心变化:从「搜仓库」变到「搜代码」

| 能力 | 未授权 | 已授权 |
|------|--------|--------|
| 搜仓库名/描述 | ✅ | ✅ |
| **搜全库代码正文** | ❌ | ✅ 关键升级 |
| 读任意仓库的文件 | ❌ | ✅ |
| 搜 Issue / 讨论 | ❌ | ✅ |
| 看 commit / release 历史 | 部分 | ✅ |
| 建仓库、推代码、提 PR | ❌ | ✅ |
| 额度 | 10 次/分钟 | 30 次/分钟 |

**为什么「搜代码」这条最关键**:仓库名和描述是作者自己写的,经常写得跟实际功能差很远,或者干脆没写。代码正文不会骗人——一个库到底有没有真的解决你的问题,搜它的实现代码最准。

上一轮我就吃了这个亏:搜「签名矢量化」返回 151 个仓库看着热闹,其实全是无关的。加了引号搜**代码正文**之后只剩 11 个文件命中,结论一下就实了。

## 二、五种实际用法

### 用法 1:想法查重(三层递进)

不只是搜一遍仓库就完事,而是三层:

1. **仓库层** —— 有人做过吗?
2. **代码层** —— 有人真的写出实现了吗?(排除"占了个名字但没写代码"的)
3. **社区层** —— 做过的人卡在哪了?

第三层往往最值钱。一个想法如果**有人尝试过并且 issue 区一堆没解决的问题**,那说明这是块硬骨头,你去做之前得先知道坑在哪。

> 你可以说:「帮我查查 XXX 有没有人做过,仓库、代码、issue 三层都过一遍」

### 用法 2:抄作业(读源码提取可复用部分)

找到最接近的那个库之后,不用整个装进来,我可以直接读它的源码,把关键那几十行扒出来给你,或者告诉它用了什么算法、什么参数。

比如你做 Excel 表格复刻,我不必让你去用 `img2table` 整个库,而是读它怎么判断表格线、怎么处理合并单元格,你把这套逻辑搬进自己的脚本。

> 你可以说:「读一下 img2table 的源码,告诉我它识别无框表格用的是什么思路」

### 用法 3:先看坑,再决定用不用

选定一个库之前,让我去翻它的 issue。常见的坑:某个平台跑不起来、某个版本之后接口变了、某个功能其实没实现、作者已经不维护了。

> 你可以说:「查查这个库有哪些已知的坑、有没有长期没解决的 issue」

### 用法 4:评估项目还活着吗

star 数最没参考价值(很多是几年前攒的)。真正说明问题的是:**最近一次 commit 是什么时候、issue 有没有人回、release 还在发吗**。

现在我能拉到这些真实数据,帮你算一个"维护活跃度"出来。选库的时候这个比 star 有用得多。

> 你可以说:「这几个库帮我比一下,哪个还在维护」

### 用法 5:把自己的东西发上去

你账号里已经有一个 `DocLayout-Agent`(基于 DeepSeek 的 Word 排版 Agent)了。像签名矢量化、学习规划这类**在 GitHub 上还是空白区**的东西,可以直接开源成仓库。

> 你可以说:「帮我把这个脚本整理成开源项目,建个仓库推上去」

## 四、边界(放心的地方)

- **不会擅自改你的仓库。** 建仓库、push、提 PR、发 issue 这类操作,我都会先跟你说清楚要做什么、等你确认。
- **不会滥用额度。** 授权后额度是 30 次/分钟,足够,但我不会无脑刷接口。
- 读代码、搜 issue 这类**只读**操作,我会直接做,不打扰你。

## 五、一句话总结

未授权时我只能回答**「有没有这个东西」**;授权后我能回答**「它是怎么做的」「用它会不会踩坑」「还值不值得用」**——以及**「要不要把你的东西也放上去」**。
